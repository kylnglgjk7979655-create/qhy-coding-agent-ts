# Code Simplifier

对本次实现引入的代码做一轮简化。目标是让代码更容易理解和维护，而不是让行数更少。行为、公开接口、错误语义、日志字段和边界条件必须保持不变。

本步骤位于 `implement` 的检查通过之后、提交之前；简化后的代码还要重新通过检查，并进入后续审查。简化必须在最终审查之前完成；审查后再改代码需要重新审查。

## 适用条件

默认只在本次实现改动足够值得时执行。以下情况可以快速浏览后跳过，并记录“跳过简化”及理由：

- 改动很小（例如新增/修改不足 50 行），且不涉及并发、进程、信号、流或生命周期。
- 改动只涉及文档、配置或文案。

涉及进程组、信号、stdout/stderr 或生命周期状态时，只做低风险简化。删除任何被捕获的状态（例如 pid 快照）都必须给出等价性证据；无法证明时保持原样。

## 1. 固定范围

- 默认只处理本次实现会话新增或修改的代码。有明确比较基准时使用 `git diff <base>...HEAD`；PR 反馈场景只处理本次反馈产生的改动。
- 可以读取相邻代码理解调用关系，但只修改本次改动及其直接关联代码。扩大范围必须有具体理由，并在报告中说明。
- 先读 `CODING_STANDARDS.md`、`GLOSSARY.md` 和相关 `docs/adr/`。仓库规范优先于本 skill 或上游示例中的任何语言偏好。
- 判断抽象是否值得保留时，可参考 `codebase-design` 的深层模块词汇：接口是否精简、是否真正隐藏了复杂度。

**完成条件：** 已列出纳入的文件和 hunk；空 diff 直接报告“没有可简化的改动”并结束。

## 2. 找可简化的地方

只检查本次改动，按收益从高到低：

- 不必要的嵌套、重复条件、可以提前返回或合并的分支。
- 本次改动内部重复的逻辑形状；只有确实重复时才抽取共享函数或类型。
- 没有说明用途的命名，或用原始类型表达领域概念。
- 散落的相关逻辑；能否收进一个模块，而不是把复杂度推给调用方。
- 解释显而易见代码的注释；TODO 是否缺少具体动作和移除条件。
- 没有调用方的参数、配置、钩子或预留扩展点。
- 过长函数、过宽接口、浅层包装；能否用更少的参数或方法表达同一行为。

同时避免过度简化：

- 不合并职责不同的逻辑，不删除真正隐藏复杂度的抽象。
- 不为减少行数使用嵌套三元、密集单行或难懂的技巧。
- 不改变公共接口、错误类型、日志字段、输出格式、边界条件或对外可观察行为。
- 不为迁就实现而弱化或改写测试；测试改动只允许消除重复 setup 或重复断言，不得修改断言值与期望。
- 不修改既有无关代码，不顺手重构。

**完成条件：** 每个候选都有位置、拟改动和收益；没有收益的候选直接排除。

## 3. 应用并验证

1. 记录简化前的检查结果，作为基线。
2. 逐项应用值得做的简化；每项都要能说明“为什么更清楚或更易维护”。
3. 先运行受影响的测试，再运行 `pnpm check`。简化后重新运行；失败必须修复后才能提交。
4. 行为保持不能只靠推断。测试通过是证据，不等于所有行为已被证明；未覆盖的风险写入报告。
5. 没有值得做的简化时，保持代码不变并明确报告。

**完成条件：** 保留的简化已全部应用；受影响检查与 `pnpm check` 通过，或明确报告未完成及原因。

## 4. 报告

- 改了什么，以及每项的理由。
- 执行了哪些检查、结果如何；区分已执行与未执行。
- 跳过或留待后续的简化及原因；扩大范围时说明理由。
- 行为等价性的证据与剩余风险。

报告随提交或 PR 证据保留，便于后续审查核对简化范围与验证结果。

本步骤不查找 Bug，也不审查需求符合性；这些分别由 `bug-review` 和 `code-review` 负责。提交、推送和 PR 由调用方完成。
