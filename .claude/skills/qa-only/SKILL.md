name: qa-only
description: 功能验收。识别 spec，生成 QA plan，实际运行产品并记录结果；用于 CR 后验收、修复后复验，或只读检查，不修改产品代码和测试。
---

通过用户实际使用的入口，验证产品是否满足 spec。交付的是运行证据和未解决的问题。

## 1. 固定比较基准

读取项目执行约定。使用调用方或项目已指定的 fixed point；没有指定时询问，无法取得时报告 blocked。确认引用有效，记录 `git diff <fixed-point>...HEAD` 及 `git log <fixed-point>..HEAD --oneline`。

记录比较基准、当前 HEAD、未提交产品改动和运行环境。检查运行入口、测试数据及所需服务，保留已有工作。

完成条件：能够定位本轮被测代码，并区分已提交代码与未提交改动。Diff 用于识别影响范围和相邻回归。

## 2. 识别 spec 来源

调用方已明确提供 spec 的 issue 引用、文件路径或完整内容时，直接使用。否则按以下顺序查找：

1. 本轮 commit message 中关联的 issue，按项目 issue tracker 约定读取。
2. `docs/`、`specs/` 或 `.scratch/` 中与当前 branch 或 feature 对应的 spec 文件。
3. 仍未找到时，询问 spec 在哪里；无法取得时记录 `no spec available`，总结果为 blocked。

使用 issue 作为 spec 时，读取正文和补充要求所在的评论。验收 parent issue 时，同时读取相关 sub-issues 的正文、状态与评论，确认完整 spec 和本轮 scope。

固定实际使用的 spec 内容，记录来源和版本或读取时间。已有 QA plan 是执行起点，须与当前 spec 核对；项目文档、示例及测试可补充执行细节和回归场景，冲突须显式澄清。

完成条件：每条预期都能追溯到具体的 spec 条目或已确认的补充要求。影响预期的歧义无人可答时，相关项目记为 blocked。

## 3. 生成 QA plan

有可用计划时沿用并补齐覆盖缺口；没有时，根据 spec 和受影响行为生成。每项包含：

| ID | Spec 引用 / acceptance criterion | 场景与操作 | 预期结果 | 环境与数据 |
| --- | --- | --- | --- | --- |

将本轮 scope 内每条 acceptance criterion 映射到至少一项检查，覆盖正常路径、相关失败路径和相邻回归。保留稳定 ID，执行中可增加发现的场景。预期以 spec 及已确认的补充要求为依据；当前实现只是被测对象。

选择足以证明该项预期的环境。优先自有、隔离的测试数据；只有与本项无关的服务可用替身。记录模拟服务不能证明的行为。要求真实服务的项目，必须取得该服务的运行证据。

完成条件：本轮每项必验行为都有 spec 引用、操作、预期和可用环境，或明确的阻塞原因。计划列好后直接执行；scope 与 spec 冲突时先澄清。

## 4. 实际执行

按 QA plan 逐项运行。先验证相关正常路径，再检查失败场景和相邻回归。每项采用同一个循环：

1. **准备**：记录 fixture 初态、输入、预期结果及准备执行的命令或操作。预期在执行前写入报告。
2. **执行**：使用项目已有的原生入口和工具，运行精确命令或完成一次明确的交互。
3. **观察**：检查输出、最终状态及相关副作用，与 spec 预期逐项比较。异步操作等待实际完成，再判断最终业务结果。
4. **留证**：立即记录实际结果、逐项状态和脱敏证据。若继续探索，先补充下一项检查的依据、预期和操作。
5. **重放失败**：从相同 fixture 初态重放失败操作，保留两次观察；间歇性问题记录复现条件和频率。确认后的问题写入报告，交由后续开发流程诊断和修复。

不同入口观察不同结果：

| 入口 | 必须观察 |
| --- | --- |
| CLI | exit code、stdout、stderr，以及相关文件或状态变化。交互式行为使用真实终端或 PTY 验证。 |
| API / job / worker | 响应、状态转换和最终业务效果。HTTP 接受或任务入队只是中间状态。 |
| 浏览器 | 实际用户操作后的页面状态、相关请求及 console；交互缺陷保存操作前后截图。 |

开发测试可作为补充证据；运行验收须使用对应入口取得实际观察。完成命令或加载页面本身不等于满足预期。

本 skill 的写入范围限于约定的 QA 产物、隔离测试数据和运行临时文件；产品代码、产品测试、项目依赖和项目配置保持不变。使用已有依赖和服务；缺少准备条件时记录 blocked，交由调用方准备后重跑。

缺陷必须包含初始条件、精确复现步骤、预期、实际结果及影响；暂未复现的异常保留原始观察和待查条件。与本次范围无关的问题单列报告。若既有问题使必验行为失败，该项仍如实记录失败；无法完成检查时记录阻塞。

完成条件：每个 QA plan ID 都有对应的执行记录和结果，或明确的未执行原因；测试启动的服务和临时资源按项目约定清理，保留诊断所需证据。

## 5. 报告

使用 [报告模板](report-template.md)，写入调用方指定的产物目录；未指定时使用新的临时目录并返回路径。保存脱敏证据，避免覆盖先前运行。

逐项状态：

- **pass**：实际结果满足预期，且有对应证据。
- **fail**：实际观察到违反预期的行为。
- **blocked**：缺少必要环境、明确预期或执行条件。
- **not-run**：尚未执行。

总结果仅在全部必验项为 pass 时为 **pass**；存在必验 fail 时为 **fail**；其余必验项未完成时为 **blocked**。与本轮无关的问题及后续人工验收要求单列。

报告绑定 spec、被测提交、工作树状态和关键环境。Spec、产品代码、配置或相关环境变化后，重新验证受影响项目，更新结论。将已有人工 QA 的真实状态保留下来。

本 skill 到报告结束；修复、提交和 GitHub 发布由其他入口负责。
