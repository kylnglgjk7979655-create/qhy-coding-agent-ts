# 工具执行框架访谈笔记

本文件归档设计访谈过程、当时的实现基线与参考资料。最终功能要求以同目录的 spec.md 为准；历史记录中的待确认措辞不代表当前仍有未决问题。

## 用户提供的停止范围参考

| 情况 | 用户描述的行为 |
| --- | --- |
| 普通工具参数错误、文件不存在、执行异常 | 单次调用失败，继续其他调用并让模型处理 |
| 流式路径中 Bash 返回错误结果 | 取消同批其他未完成调用，之后仍可让模型继续 |
| 用户中断、父级 abort 信号触发 | 结束当前执行轮次 |
| Hook 明确要求停止继续 | 结束当前执行轮次 |
| 达到 maxTurns | 停止继续调用模型 |
| 上下文超限且无法恢复 | 停止当前轮次并显示错误 |
| 模型/API/流处理错误无法恢复 | 停止当前轮次并显示错误 |
| 严格配对模式发现消息异常 | 抛错，拒绝发送下一次请求 |
| 默认配对修复后仍被 API 拒绝 | 显示 API 错误，结束当前轮次 |

用户已确认此表仅作为参考，不表示本仓库现状或首版完整目标。适用于首版的停止规则以“已确认的方向”为准；默认配对修复明确不纳入，配对异常直接拒绝。

## 访谈时的实现基线

- `src/agent.ts` 中内联定义 `runtimeInfo`、`read_file`、`write_file`，由 `ToolLoopAgent` 调度，SDK 根据各工具提供的 Zod schema 校验参数。
- 文件工具自行捕获错误并返回 `{ error: string }`；成功结果形状各异，尚无应用层统一结果协议。
- SDK 关联工具调用与结果的调用 ID；应用层未增加 ID 校验。
- 应用层未承诺同批工具调用的执行顺序；这与本次已确认的顺序要求存在差距。
- 已安装 SDK 支持 `toolCallConcurrency: 1`，可按模型生成顺序串行执行，且普通工具执行失败不会自动中止队列。无需为实现顺序单独建立执行队列；仅关闭 provider 的并行调用选项不足以保证本地顺序。
- 当前 Zod 对象 schema 默认剥离额外字段；字符串字段不做类型转换。`runtimeInfo` 会接受带额外属性的对象并将其剥离为 `{}`。
- SDK 原生错误结果经当前 OpenAI Chat 适配后不会自动带有 `is_error` 字段。本设计将该字段定义为应用层工具输出协议。
- 工具名在步骤结束后通过回调展示；尚无应用层工具开始、成功、失败事件。
- SDK 提供执行开始和结束回调；参数校验失败不会进入实际执行回调，若要展示这类拒绝结果，需要额外适配。
- 已有文件工具规格要求终端仅展示工具名称；本规格将展示扩展为工具名称与状态，参数和完整结果仍交给 Agent，不作为工具输出打印。
- 本仓库尚无 Bash 工具、Hook 停止机制、`maxTurns`、上下文恢复流程或严格/默认配对修复模式。现有配置使用 `maxSteps` 与 `timeoutMs`。
- 当前 Ctrl+C/SIGTERM 不仅取消当前轮次，还会退出 CLI；本次已确认保留此行为。
- 冒烟判定直接将工具输出视为 `{ content: probe }`；采用统一成功包装后必须同步适配为校验 `output.content`。
- 历史工具输出由应用原样交给 SDK，应用不读取其中业务字段；旧历史可以保留原格式，与新调用结果混存，无需因包装变更迁移。

### 第二轮

- Q4（执行事件）：用户答复“可以有”，确认支持执行事件。
- Q5（校验与 ID 关联职责）：用户答复“继续复用”，确认保留 SDK 对应能力。

- 对 Q6 的现状核实：当前文件工具错误是 `{ error: string }`，尚无 `is_error` 字段；当前应用层也尚未保证同批调用按模型顺序执行。已确认的是本次目标语义。
