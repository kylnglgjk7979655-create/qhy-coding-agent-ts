# 对话摘要替换历史，仅随成功轮次保存

父需求 #6 的子任务 #14 建立摘要与历史替换路径，子任务 #15 将预算检查扩展至 SDK 每次主模型请求。预算包含内置系统提示、消息以及本轮实际可用的工具名称、描述和参数 schema；使用序列化载荷的字节数和消息开销估算，不声称与模型精确 token 数相同。容量、回答预留、触发阈值、压缩目标及完整保留轮数均经过严格配置校验。

默认达到可用输入预算的 80% 时，通过独立模型请求生成摘要，保留最近两轮完整对话及当前轮次，目标为压缩到预算的 50% 以下。按用户消息划分轮次，整轮保留工具调用与对应结果，不通过截断消息满足预算。摘要请求默认复用主模型配置，不暴露可执行工具；要求保留目标、已确认决策、约束、关键结果和未完成事项。

摘要以 assistant 历史资料替代较早消息，不能改变产品内置系统提示或工具策略；不将摘要作为 system 消息，不自动读取开发用 AGENTS.md 或发现运行时规则文件。公共运行入口的 effectiveHistory 是 CLI 保存与后续对话的唯一历史交付结果，responseMessages 仍表示当前轮次响应。

通过有效性及预算检查后，本轮使用替换后的内存历史；成功完成轮次后，沿用临时文件加原子替换，持久化摘要、覆盖边界及保留消息。跨进程直接加载有效历史复用已保存摘要，旧格式历史保持可读并按需摘要。

摘要生成失败、响应无效、必要内容无法容纳或压缩后仍不达目标时，以明确轮次错误停止，不发送本轮后续主模型请求，不无限摘要或自动删消息。摘要成功后轮次失败或取消，同样不覆盖上次成功的磁盘和可续聊内存历史。已经发生的工具副作用不回滚。

同轮工具结果增长后，借助 SDK 的 prepareStep 在下一次主模型请求前重新检查并替换较早历史；当前轮次的完整工具调用和结果保持配对，替换后的消息继续用于后续步骤。成功结果的 effectiveHistory 使用最后一次准备的历史及尚未包含的新响应，避免恢复旧原文或重复追加本轮消息；responseMessages 保持本轮完整响应的兼容语义。

独立审查和摘要请求自身也受输入预算约束。审查估算专用提示、当前完整调用、适用权限规则、环境描述及该 Agent 有效历史中的摘要、用户文本和提取后的工具调用记录；不加入原始工具结果或当前调用的重复历史。子 Agent 只使用自身上下文。摘要估算专用提示与待替换原文。任一请求自身无法容纳时直接报 CONTEXT_ERROR，不发出该请求，不尝试分段摘要、截断调用或规则、删消息，也不另建审查摘要。回答预留同样限制两种独立请求的输出。

审查、摘要与主模型请求使用同一整轮取消信号并消耗剩余执行时限，取消和超时均停止后续处理。独立请求不重置主模型步骤计数；人工审批等待仍单独计时，不重置此前已消耗的执行预算。

## 后续决策：完整 transcript 与有效历史分离（Issue #31）

用户级会话记录同时保存完整原文 transcript 和供下一轮模型请求使用的 `effectiveHistory`。每轮开始先持久化用户消息、运行状态与本轮生效配置；流式文本、模型工具调用及工具结果在观察到时更新 transcript。成功轮次以 SDK 最终消息替换本轮暂存的进度消息，并更新 `effectiveHistory`；失败或取消轮次保留已观察内容和终态，但不更改上次成功的有效历史。摘要只允许替换有效历史，不删除或压缩 transcript。

## 后续决策：保存摘要及覆盖边界（Issue #33）

成功轮次将新生成的摘要与 `effectiveHistory` 一并保存到会话记录。`summaries` 保存摘要正文及 `coversThrough`，其值表示 transcript 中被覆盖消息区间的排他结束位置；后续摘要从上次边界继续计算。恢复时直接使用已压缩的 `effectiveHistory`，不重复摘要或重放其覆盖消息。兼容旧工作区历史时，迁移进会话的原始消息同时作为 transcript 初始内容，避免摘要后失去原文。

每次 transcript 更新仍通过临时文件和原子替换完整写入会话记录。写入失败即停止本轮后续模型请求和工具操作；此前已经完成的文件、宿主或远端副作用不回滚，也不标记为已回滚。

## 后续决策：Skill 正文注入与轮次边界（Issue #128）

Skill 调用成功后，程序在下一次模型请求前把 `Skill: <规范名称>` 标头与正文作为独立 user 消息加入消息序列，排在对应工具结果之后；工具结果与该消息在有效历史、完整 transcript 中各自独立并保持先后顺序。注入消息由程序生成，随有效历史保存并在续聊请求中继续提供，因此续聊看到的是当时实际提供给模型的正文。

注入消息不进入系统指令，不改变工具策略或权限；它也不参与轮次切分，压缩计算保留轮次时按普通 user 消息之外的标记识别，避免当前轮的用户消息与工具往返被摘要替换。注入发生在 prepareStep 内并随 SDK 的步进消息延续到后续步骤，因此同一运行内后续请求不会重复注入同一次调用。

## 后续决策：Skill 加载顺序记录（Issue #129）

会话记录新增可选字段 `skillLoads`，按最近实际加载顺序保存 Skill 规范名称。成功轮次内的多次注入按发生顺序合并，同一 Skill 重复加载只保留最近一次位置；字段随会话记录原子写入，跨进程续聊可读取当时的加载顺序。缺少该字段的旧记录保持可读，历史重建与摘要边界行为不变。加载记录随成功轮次保存，与有效历史一致；失败或取消轮次不写入新的加载顺序。

## 后续决策：压缩后恢复 Skill 正文（Issue #130）

压缩生成摘要后，程序把已被摘要移除的 Skill 正文按最近实际加载顺序（最近优先）作为程序生成 user 消息恢复到摘要之后的 `effectiveHistory`；正文仍留在保留轮次中的 Skill 不重复添加，恢复内容取注册时读入的正文。恢复只替换有效历史，不改写完整 transcript、系统指令或工具策略，也不改变摘要正文。

摘要覆盖边界仍按 transcript 消息计算：恢复正文不在 transcript 中，`summaries` 新增可选 `restoredMessages` 记录该摘要恢复的正文条数，后续摘要据此从覆盖边界中扣除，避免 `coversThrough` 越界。缺少该字段的旧记录按 0 处理。
