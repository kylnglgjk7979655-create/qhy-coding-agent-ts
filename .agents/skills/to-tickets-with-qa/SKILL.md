# 拆分工单与最终人工 QA

将计划、规格或当前对话拆成独立的垂直切片实现工单，最后追加一张人工 QA 工单。每张工单声明阻塞它的其他工单。

## 1. 收集上下文

沿用当前对话中已有的讨论。用户传入规格路径、工单编号或 URL 时，读取其完整正文和评论。

读取项目的 `AGENTS.md` 及其中指向的工单系统、状态和领域文档约定。缺少工单系统配置时，提示用户先运行 `/setup-matt-pocock-skills`。

本地会话使用本地 Markdown 工单，具体布局见 `docs/agents/issue-tracker.md`，状态名称见 `docs/agents/triage-labels.md`。新建工单正文使用中文，保留模板中的机器可读字段名和状态值。

GitHub Actions 传入父 Issue 时，按 [项目执行适配](../../../docs/agents/skill-execution.md) 使用原生子 Issue 和依赖关系。无人值守的规划轮只输出待审批计划；用户检查该计划并添加 `agent:publish-tickets` 后，由发布脚本创建工单。本 skill 的计划确认、人工 QA 和父规格状态规则在两种入口均生效。

## 2. 按需探索代码

尚未了解相关代码时，探索当前实现，使用项目领域词汇，并尊重相关 ADR。

寻找能让实现更简单的预备重构机会：“先让改动变容易，再做这个容易的改动。”

## 3. 拆分垂直切片

每张实现工单是一条 tracer bullet：穿过相关层的狭窄但完整的行为路径。

- 覆盖该行为涉及的 schema、API、UI、测试等层，而非按层拆票。
- 完成后可以独立演示或验证。
- 大小适合在一个全新的上下文窗口内实现。
- 必要的预备重构排在依赖它的功能之前。

为每张工单声明真实阻塞关系；没有阻塞项的工单可以立即开始。

跨全库的机械重构是例外：如果一次改名或类型变更会同时破坏大量调用点，采用 expand–contract。先添加兼容的新形式，再按影响范围分批迁移，最后在所有迁移完成后删除旧形式。各批次依靠兼容形式保持 CI 通过；无法独立保持通过时，使用共享集成分支，并增加依赖全部迁移批次的集成验证工单。

每张实现工单保留自己的验收标准，描述可观察的行为；最终人工 QA 验证这些切片组合后的运行结果。

## 4. 生成最终人工 QA 工单

始终追加一张标题为 `QA: <功能名称>` 的工单，作为本次依赖图的最后一项，依赖本次全部实现工单，包括预备重构和集成工作。

依据源需求和拟定切片编写 QA 计划，覆盖完整用户流程、跨切片配合、重要异常与恢复路径，以及相关的权限和第三方集成。范围限定在本次功能及可能受影响的既有行为。没有 UI 的任务，通过真实 CLI、API 或其他可观察入口验收。

每项检查写清前置条件、具体操作或输入、可观察的预期结果。提供启动方式、所需账号、测试数据、服务及配置项名称。已核实的运行命令可以直接写入；不确定的准备步骤标记为待确认，配置只写变量名，不写密钥值。

单测和代码审查是辅助证据，通过它们不等于完成人工 QA。生成工单时，所有检查保持未勾选，结果为待人工执行。实际验收时由人记录测试版本、环境、通过或失败结果以及阻塞原因；失败项附复现步骤，已有后续缺陷工单时附链接。只有人在确认结果和明确接受的例外后，才能关闭 QA 工单。

## 5. 展示拆分并确认

以编号列表展示全部拟定工单，包括最后的 QA 工单。每项展示：

- 标题。
- 执行方式：Agent 或 Human QA。
- 阻塞项。
- 交付或验证的完整行为。

同时展示 QA 的准备条件和检查清单，让用户能审阅实际验收内容。

询问粒度是否合适、依赖是否真实、是否需要合并或继续拆分，以及 QA 是否覆盖完整流程和关键风险。迭代至用户批准这份拆分。

## 6. 发布工单

按依赖顺序发布，最后发布 QA 工单，使阻塞关系可以引用已存在的编号。

- 本地文件：每张工单一个文件，放在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，从 `01` 开始按依赖顺序编号。最后的 QA 文件使用 `<NN>-qa.md`。已有工单时沿用编号，避免覆盖无关文件或重复创建同一工单。
- 真实工单系统：每张工单独立发布，优先使用原生阻塞关系，否则在正文声明阻塞项。源文档是已有父工单时，按项目配置的操作建立子工单关系。

实现工单使用项目的 `ready-for-agent` 状态。QA 工单使用 `ready-for-human`，声明 `Execution: Human QA (HITL)` 并保留全部阻塞关系；即使所有依赖完成，它也不能进入 AFK 队列。

Agent 的可领取集合只包含阻塞项全部完成的实现工单。实现结束后，最终 QA 等待人执行。本 Skill 的完成条件是已发布批准的工单和 QA 计划，并给出文件路径或链接；本次拆票不执行 QA，也不把清单勾成通过。

保留父规格及父工单的内容和状态。

## 实现工单模板

本地文件使用以下模板；真实工单系统可以将父引用和依赖转换为原生关系。

```markdown
# <NN>: <标题>

**Parent:** <源规格或父工单引用，没有则省略>

**What to build:** <从用户角度描述完整行为，而非按代码层罗列实现任务>

**Blocked by:** <依赖工单的编号和标题；没有则写 None (can start immediately)>

**Status:** ready-for-agent

- [ ] <可观察的验收标准>
- [ ] <可观察的验收标准>
```

## 最终人工 QA 工单模板

```markdown
# <NN>: QA: <功能名称>

**Parent:** <源规格或父工单引用，没有则省略>

**Execution:** Human QA (HITL)

**Blocked by:** <本次所有实现工单的实际编号和标题>

**Status:** ready-for-human

依赖项全部完成后，由人执行验收。

## 准备

<启动方式、测试账号或角色、数据、服务、配置项名称及仍待确认的准备条件>

## 人工验收

按完整用户流程分组，每项使用以下格式：

- [ ] <可观察行为，引用对应需求或实现工单>
  - 前置条件：<初始状态和测试数据>
  - 操作步骤：<具体、有顺序的操作或输入>
  - 预期结果：<能够判断成功或失败的可观察结果>

## 验收记录

待人工执行。记录测试版本和环境、各项通过/失败/阻塞结果、失败复现步骤，以及已有后续缺陷工单的引用。未验证项保持未勾选。
```

实现工单通常不写具体代码路径或代码片段，以免快速过期。原型中精确表达已定决策的状态机、类型或 schema 片段可以精简后内联，并注明来源。QA 中可保留执行检查所需的命令和 fixture 引用。
