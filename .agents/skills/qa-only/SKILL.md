# 只读 QA

通过用户实际使用的入口，证明产品满足 spec。交付运行证据和未解决的问题。

**先写预期，再运行，最后用证据下结论。** 预期来自 spec，实际结果来自产品运行。

## 1. 固定被测版本

读取 `AGENTS.md`、`CODING_STANDARDS.md` 和 `docs/agents/skill-execution.md`。

使用调用方或项目指定的比较基准（fixed point）。未指定时询问，无法取得则报告 blocked。确认引用有效，记录其 SHA，以及 `git diff <fixed-point>...HEAD` 和 `git log <fixed-point>..HEAD --oneline`。

按 [报告约定](report-template.md) 记录 HEAD、工作树指纹和运行环境。Diff 用于确定影响范围和相邻回归；保留已有工作。

使用调用方指定的产物目录；未指定时创建 `.scratch/qa/<run-id>/`，`run-id` 使用 `YYYYMMDD-HHmmss-<被测 HEAD 前 7 位>`。同一 run 的复验沿用原目录。

完成条件：能够定位被测代码、工作树状态和产物目录。

## 2. 找到 spec

优先使用调用方提供的 issue、文件或完整内容。否则依次查找：

1. 本轮 commit message 关联的 issue，按项目 issue tracker 约定读取。
2. `docs/`、`specs/` 或 `.scratch/` 中对应当前分支或功能的 spec。
3. 询问调用方。仍无法取得时，记录 `no spec available`，总结果为 blocked。

Issue 要读正文和补充要求所在的评论；验收父 Issue 时，还要读相关子 Issue 的正文、状态与评论，确认完整需求和本轮范围。

固定实际使用的 spec 内容，记录来源和版本或读取时间。已有计划须与当前 spec 核对；项目文档、示例和测试用于补充执行细节。影响预期的冲突须澄清，无人可答时将相关项记 blocked。

完成条件：每条预期都能追溯到具体 spec 条目或已确认的补充要求。

## 3. 制定 QA plan

先检查运行入口、测试数据和所需服务。有计划时读入产物目录中的 `qa-plan.md`，保留 ID，补齐覆盖缺口；没有时先跑一次真实入口探索，例如 `--help` 或启动命令，记录所需账号、初态和探索证据。含视觉项时按 surface 采集探索截图。

在 `qa-plan.md` 中记录 spec 来源与版本、探索记录、风险项（没有则写「无」），以及：

| ID | Spec 引用 / acceptance criterion | surface / 入口 | 前置数据 | 步骤 | 预期结果 | 证据形式 |
| --- | --- | --- | --- | --- | --- | --- |

同时列出逐条需求覆盖表：`需求引用 → 检查 ID → 必验 / 范围外及依据`。一项检查可覆盖多条需求，但每条都须有对应步骤和断言；检查数量不作为覆盖证明。覆盖正常路径、相关失败路径和相邻回归，涉及不同触发条件的行为分别验证。ID 保持稳定，执行中可补充新场景。

执行前校验预期、fixture、脚本和断言：需求要求拒绝的操作应验证拒绝；配置、变量和服务须满足步骤前提。验收文档时，从干净初态按文档原命令和顺序执行，记录变量的定义、导出、透传及进程边界。任何必要改写都单列依据与局限，原示例仍须有自己的验收结论。

按 [surface 分派](surfaces.md) 选择 `web`、`android`、`ios`、`harmony`、`desktop` 或 `native`，取得足以证明预期的运行证据。优先使用隔离数据；仅与本项无关的服务可用替身，记录模拟范围及其证据局限。要求真实服务的检查必须取得真实服务证据。

完成条件：每个必验行为都有完整检查项，或明确的阻塞原因。范围与 spec 一致后直接执行。

## 4. 运行与留证

写计划和执行前，按 [风险操作与授权](permissions.md) 检查具体操作。需要新增授权时保留已完成结果，停止本轮执行并报告。

先跑正常路径，再跑失败场景和相邻回归。每项使用同一个循环：

1. **准备**：在报告中写入 fixture 初态、输入、预期和精确操作。
2. **执行**：通过项目已有入口完成命令或交互。
3. **观察**：对照预期，检查输出、最终状态和相关副作用。异步任务等到业务完成再判断。
4. **留证**：立即保存实际结果、状态和脱敏证据。继续探索前，先补充下一项的依据、预期和操作。
5. **重放失败**：从相同初态重跑，保留两次观察。间歇性问题记录触发条件和频率；暂未复现的异常保留原始观察和待查条件。

先完成本轮可执行项，阻塞和未执行项记录原因。失败后先核对需求依据、实际命令、fixture 与断言，区分产品 / 文档、QA 自身、环境或需求冲突；分类写入 findings。确认 QA 产物有误时，在只读边界内修正并重跑，保留原始观察、纠正依据与撤销记录。已有有效失败证据的偶发问题保留 fail，后续通过不能单独证明已解决。

不同入口需要不同观察：

| 入口 | 必须观察 |
| --- | --- |
| CLI | exit code、stdout、stderr、文件或状态变化；交互行为在真实终端或 PTY 中验证。 |
| API / job / worker | 响应、状态转换、最终业务效果；请求接受或任务入队后继续观察。 |
| 浏览器 | 用户操作后的页面状态、相关请求与 console；交互缺陷保留操作前后截图。 |

确定性检查优先用原生入口，需要渲染证据时按 surface 约定追加桌面截图。开发测试可补充证据，验收结论必须有对应入口的实际观察。

缺陷记录初始条件、精确复现步骤、预期、实际结果和影响，使用稳定 ID（`D1`、`D2`…）关联 QA 检查 ID；复验沿用 ID 和历史，误报撤销使用 `invalidated`。范围外问题单列；既有问题导致必验行为失败时仍记 fail，无法完成检查时记 blocked。

完成条件：每个检查 ID 都有执行记录和结果，或明确的未执行原因。清理本轮启动的服务和临时资源，保留诊断证据。

## 5. 报告

按 [报告模板与判定规则](report-template.md) 更新 `report.json`，据此生成 `report.md`，证据写入 `evidence/`。保留已有人工 QA 的真实状态；交付前完成模板中的一致性核对。

**全部必验项有通过证据，才能判 pass。** 实际观察违反预期记 fail；缺少环境、明确预期或执行条件记 blocked。完整逐项状态、总结果优先级和证据路径约束见报告模板。

Spec、代码、配置、QA 脚本或相关环境变化后，按报告约定重跑受影响项，保留各轮历史和证据。复用已有 runner，以检查 ID 选择执行范围；修改 runner 后重跑依赖其变更逻辑的检查。

## 只读边界

写入范围限于 QA 产物、隔离测试数据和运行临时文件。保持产品代码、产品测试、依赖和配置不变；使用已有依赖和服务，缺少条件时报告 blocked，交调用方准备后重跑。

本 skill 到报告结束。修复与本地提交由 `qa` 等开发入口负责；GitHub 发布按项目执行约定处理。
