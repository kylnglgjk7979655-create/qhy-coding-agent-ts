# QA

QA 是 **验收 → 分诊 → 修复 → 独立复验** 的循环。每次修复都回到真实入口，证明用户遇到的问题已经解决。

**验收结论来自独立运行的 `qa-only`。** 修复代理交付代码，验收代理交付证据。主代理维护状态、决定下一步。

## 1. 固定本轮输入

读取 `AGENTS.md`、`CODING_STANDARDS.md` 和 `docs/agents/skill-execution.md`。固定：

- **比较基准**（fixed point）：调用方指定的引用，默认 `main`。确认引用有效，记录其 SHA。
- **Spec 来源**：issue、文件或链接。由验收代理读取并固定实际使用的版本。
- **被测版本**：当前 HEAD、未提交产品改动和运行环境。保留已有工作。
- **整轮预算**：调用方可指定；默认总计最多 3 轮批量修复、2 次审查、60 分钟。每个缺陷最多修复 3 轮。时间从本轮开始累计，恢复、发现新缺陷或更换代理均不重置；只有调用方明确调整才更新预算。

创建 `.scratch/qa/<run-id>/qa-loop.json`，按 [循环状态](loop-state.md) 初始化。`run-id` 使用 `YYYYMMDD-HHmmss-<起始 HEAD 前 7 位>`；整轮复用同一目录，HEAD 变化后也沿用。

完成条件：能够定位被测代码、需求来源、本轮产物及整轮停止条件。

## 2. 验收

派独立的 `qa-only` 子代理，传入本轮输入和产物目录。它独立读取 spec，生成需求覆盖表和 `qa-plan.md`，实际运行产品，写入报告和证据。先完成首轮计划中可执行的检查，阻塞和未执行项写明原因，再批量分诊与修复。

- **pass**：进入审查。
- **fail**：进入分诊。
- **blocked**：补齐授权范围内的环境条件，重跑阻塞项；无法补齐时保留现场并结束。

阻塞项等待执行条件齐备后再验收，不进入缺陷修复循环。

## 3. 分诊

逐项核对失败检查的 spec 原文、实际操作、fixture 和断言，记录分类、依据与处理：

| 分类 | 处理 |
| --- | --- |
| 产品 / 文档缺陷 | 明确违反哪条需求；修复前核对拟改行为仍符合该需求，确认后进入修复。 |
| QA 预期 / 脚本 / fixture 错误 | 由 `qa-only` 修正验收产物并重跑，保留误报记录；撤销的缺陷标记 `invalidated`。 |
| 环境条件缺失 | 按第 2 步处理阻塞。 |
| 需求冲突 / 原因未明 | 保存观察和待查条件，先澄清或定位；预期无法确定时记 blocked。 |

安全策略、权限、接口契约、兼容性等变更，须在修复方案中引用需求依据。需求明确要求拒绝的行为，以拒绝作为预期；验收便利不能成为放宽产品约束的依据。已有证据确认的失败，在原因未明或偶发重跑成功时仍保留 fail。

完成条件：每个失败都有分类与依据；只有确认的产品或文档缺陷进入修复。

## 4. 修复与复验

派 `implement` 子代理，一次修复本轮已确认且预算允许的缺陷。传入需求依据、允许修改的行为及回归范围；使用报告中的稳定缺陷 ID（`D1`、`D2`…），保留与 QA 检查 ID 的对应关系。

能由原生测试复现的缺陷，先运行失败测试，再修复。视觉或设备缺陷由 `qa-only` 实际复验，不新增 Midscene 测试文件。修复后运行仓库要求的检查，返回 commit SHA。

再派独立的 `qa-only` 子代理，自行核对需求与修复后的版本，重跑失败项和相邻回归项。修复触碰共享代码时，重跑所有受影响检查；影响无法界定时重跑全部必验项。证据沿用和失效规则见 [报告约定](../qa-only/report-template.md)。

复验保留 QA 检查 ID，更新整份计划的总结果。通过后进入审查，阻塞按第 2 步处理，仍有失败则回到分诊。

一轮是一次批量修复及其复验；派发修复时即占用一轮，并增加实际尝试缺陷的次数，中断也保留计数。时间限制适用于所有阶段；轮数和次数限制用于判断能否启动下一次修复或审查，允许已获预算的最后一轮完成复验与收口。无法继续时保存状态、清理并报告剩余问题。QA 脚本纠错与阻塞准备也计入整轮时间。

本轮已无可修复缺陷、必验项仍失败时，报告未解决项并结束。

## 5. 全绿后审查与最终收口

全部必验项通过后，派 `code-review` 子代理，分别审查编码规范和需求符合性。

第一次审查前固定审查基准，之后保持不变：本轮修过代码时，使用**首次修复前的 HEAD**，并提供当时已有产品改动的快照以区分本轮增量；首轮验收即通过时，使用开始时的比较基准。需求符合性判断始终读取完整 spec，包含相关父子需求与补充要求。

传入审查基准到当前 HEAD 的 diff、当前暂存 / 未暂存差异及相关未跟踪产品文件，使审查覆盖实际被验工作树。确认没有待审产品改动时记录依据，审查记 `not-applicable`。

有效 finding 关联或新增检查与缺陷，回到第 3 步。新缺陷分配新 ID，同一缺陷再次出现时沿用原 ID 和次数；它们共同受整轮预算限制。

审查仍有有效 finding 且次数已耗尽时，记录未解决项并结束。审查结论绑定被审版本；审查后的产品改动使受影响的审查结论失效。

交付前核对最终 HEAD、工作树与运行环境是否匹配独立验收和审查记录。最后一次产品改动（含文档）之后，受影响项必须由独立 `qa-only` 复验；主代理的补验可作补充证据。版本未变且证据有效时沿用已有结论，无需为收口重复整轮运行。

完成条件：最终目标的全部必验项通过、需求覆盖完整、有效审查无未解决 finding，且报告一致性核对通过。验收结果、循环完成状态和停止原因分别记录；预算耗尽时仍保留实际结果。

## 委派

每次派发给出目标、工作目录、产物目录、比较基准、被测版本、相关检查 / 缺陷 ID、需求快照路径、授权边界、剩余预算及预期返回结构。默认使用全新上下文，支持时显式设置 `fork_turns=none`；子代理按指针自行读取项目约定、需求与证据。验收代理独立判断预期，修复摘要仅提供定位线索。

主代理保存来源指针，只接收总结果、失败项 ID、commit SHA、证据路径和 findings 摘要。完整 diff 和截图留在子代理上下文中。

上下文重、可独立完成、返回结果足以支持主代理判断时才委派。独立验收保留上述分工；轻量状态更新和条件判断在主代理中完成。使用运行时的完成通知；需要主动等待时使用其支持的长等待，超时后仅更新必要进度，避免反复短等待和无进展唤醒。

同一 run 复用参数化 runner，以检查 ID 选择复验范围，每次输出独立证据。主代理维护循环元数据、分诊与审查 finding 的登记，同步缺陷生命周期；实际观察与验收判定由 `qa-only` 更新，Markdown 从当前 JSON 生成。仅在运行时提供实际 usage 时记录 token，区分输入、缓存输入和输出，不据累计输入推算费用。

## 风险与范围

验收和修复都遵循 [风险操作与授权](../qa-only/permissions.md)。已有授权覆盖操作与目标时直接继续；需要新增授权时保留结果并停止循环，说明具体操作、必要性、影响范围和替代方案，等待批准。主代理不代替用户批准。

允许本地 commit。push、PR 和共享分支操作按上述授权规则处理。修改范围不含 `.sandcastle/`、workflow 和 CI；当前仓库的 QA 入口为本地会话。

## 交付

按 [循环状态](loop-state.md) 更新状态文件和最终报告。返回 `report.md` 路径、实际验收结果、循环完成状态、停止原因、被验版本、已提交 commits、审查结果、未解决项和待授权操作。

**轮次耗尽不代表通过。** 保留实际验收结果，明确标记循环未完成及停止原因。blocked 保留现场与证据，供条件齐备后恢复。
